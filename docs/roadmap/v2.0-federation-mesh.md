# v2.0 — Federation + Mesh

> **Codename**: Federation + Mesh
> **Target**: 2028 H2+
> **LOC ceiling**: 30,000 (ceiling already reached; v2.0 features must remove old code to add new)
> **Persona**: Data mesh shops, large enterprises with domain-oriented data ownership
> **Theme**: Cross-org Iceberg catalog federation + Data Mesh Mode 3 formalized.

---

## Theme: "Data Products That Travel Across Org Boundaries"

v2.0 is the formalization of **Mode 3** from the yield-to-giants strategy: Iceberg REST catalog federation for Data Mesh. Data products created in one team's Nucleus project are discoverable and consumable by other teams without data movement.

This is NOT about Nucleus becoming a "platform platform" or an enterprise middleware. It is about Nucleus being the ideal *data product* tool for a team that participates in a larger data mesh.

---

## Features

### 1. Iceberg REST Catalog Federation

Per `docs/specs/nucleus_architecture_v4.1.md` §10.3 (Mode 3):

- `nucleus federate <asset-key> --to <catalog-url>` — registers an asset in a remote Iceberg REST catalog
- Remote teams can read the Iceberg table without knowing Nucleus's internals
- Auth: OIDC JWT delegation (no password sharing)
- Supported remote catalogs: Lakekeeper, Apache Polaris, AWS Glue, Databricks Unity Catalog, Snowflake Horizon

### 2. Data Product Marketplace

Per `docs/specs/nucleus_architecture_v4.1.md` §18.7:

- `nucleus marketplace publish <asset-key>` — lists the asset in the Nucleus Cloud marketplace
- Other teams discover, subscribe to, and pull data products via the marketplace
- SLA metadata attached: freshness guarantee, schema stability tier, owner contact
- No data movement: marketplace is a metadata registry; actual data stays in the producer's Iceberg catalog

### 3. Cross-Org Asset Graph

- `ctx.read("org://other-team/their-asset")` — read a federated asset using OIDC delegation
- Lineage spans org boundaries (producer → consumer tracked in OpenLineage events)
- Workbench visualizes cross-org dependencies

### 4. Multi-Region Deployment

- Cloud tier supports US-East, EU-West, AP-Southeast regions (for data residency)
- Iceberg catalogs are region-local; federation handles cross-region reads with latency awareness

### 5. Nucleus Plugin SDK (First External Plugins)

Per `docs/specs/nucleus_architecture_v4.1.md` §20.2 (non-goal review):

- v1.x: no public plugin SDK
- v2.0: first review of plugin SDK feasibility
- If shipped: limited to *connector* plugins (new ingest sources) and *check* plugins (new data quality rules)
- Explicitly excludes: engine plugins, orchestration plugins (those stay Tier 1/2 internal swap only)

## 30K LOC Ceiling Management at v2.0

The proprietary code ceiling has been reached since v1.5. v2.0 features ship by:

1. **Removing deprecated code** — APIs deprecated in v1.5 are removed in v2.0.
2. **Extracting to separate packages** — vertical packs, connector plugins, marketplace client.
3. **Offloading to OSS** — contributions to upstream projects (pyiceberg, OpenLineage) for features that belong there.

The 30K LOC ceiling is non-negotiable. If a v2.0 feature requires more LOC than available, it ships as a separate package outside the ceiling.

---

## Non-Goals Even at v2.0

- Hyperscale (>100TB single-pipeline) — never; yield to Databricks/Snowflake
- LLM training / model serving — out of scope forever
- Owning any Tier 0 standard (Iceberg, Arrow, etc.) — we contribute but never control

---

## Yield-to-Giants at v2.0 — What "Federation" Means

Mode 3 is not a competitor to Databricks Unity Catalog or Snowflake Horizon. It is **complementary**:

- Teams using Nucleus as their team-level data product tool can **federate** into a larger mesh governed by any Iceberg-compatible catalog.
- Nucleus is the **producer tool**; the enterprise catalog is the **mesh fabric**.
- "Friendly to giants" means federation makes Nucleus *more valuable* alongside Databricks/Snowflake, not instead of them.
