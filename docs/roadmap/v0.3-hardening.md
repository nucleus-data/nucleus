## Theme: "What breaks in real usage — fix it"

v0.3 is driven by post-launch telemetry and external-tester feedback, not by the founding team's intuition. Features in this phase ONLY land if they clear at least one of:

1. **Empirical trigger**: telemetry shows >5% of user sessions encounter this failure mode.
2. **Tester explicit request**: PoC #5 testers or early GitHub Issues call it out with reproduction steps.
3. **Architectural prerequisite**: required to unlock a v0.5+ feature (e.g., Lakekeeper is the gate for REST catalog).

This rule exists to prevent scope creep. The 8-question gate still applies to every item.

## Feature Priority Order

### 1. Chaos Test Infrastructure

**Why first**: Without chaos tests, reliability improvements are guesses. Chaos tests provide empirical evidence of exactly what breaks.

**What**:
- Docker Compose setup with kill switches (`docker compose kill minio`, etc.)
- Test fixtures that simulate: MinIO going down during a write, Dagster process killed mid-materialization, concurrent materializations of the same asset, network partition between DuckDB and MinIO
- CI step: `pytest tests/chaos/ --chaos-mode` (tagged `@pytest.mark.chaos`, run nightly not on every PR)

**Acceptance**: At least 5 chaos scenarios covered; all result in `NucleusError` subclasses (no raw exception leaks).

**Effort**: ~200 LOC in test harness; coordination in `tests/chaos/conftest.py`.

**Wrap target**: None; this is test infrastructure only.

### 2. Concurrent Run Safety

**Why**: Two engineers triggering `nucleus run` simultaneously on the same asset produces undefined behavior. This is a day-one pain for startup teams.

**What**:
- Filesystem advisory lock (fcntl on Linux, msvcrt on Windows) in the AMA before any Iceberg commit
- Timeout: 30 s default; configurable in `nucleus_project.yaml`
- Error: `NucleusCommitConflictError` (NE1002 — already exists) with actionable fix_hint

**Acceptance**: `test_concurrent_run_same_asset_serializes` passes (second run waits or fails cleanly, no half-written snapshots).

**Effort**: ~50 LOC in `coordination/asset_materialization.py`. No new dependency.

### 3. Iceberg Time-Travel Queries

**What**: `nucleus query --snapshot=N <sql>` — query any asset "as of" Iceberg snapshot N. Uses pyiceberg's `load_snapshot_by_id` (verified API: https://py.iceberg.apache.org/api/).

**Acceptance**:
- `nucleus query --snapshot=<id> "SELECT COUNT(*) FROM my_asset"` returns results from that snapshot
- Invalid snapshot ID raises `NucleusAssetNotMaterializedError` (NE1009)

**Effort**: ~80 LOC in `cli/commands/query.py` + `ctx/read.py` extension.

### 4. dlt 100+ Connectors (ADR-014 Stage 2)

**Why**: `ctx.copy_from` covers SQLite, Postgres, MySQL (v0.1). The beachhead team often needs: REST APIs, CSV files, Google Sheets, Salesforce. dlt covers all of these with verified sources.

**What**: Expose dlt's verified-source ecosystem via `nucleus ingest <source>://<path>`. Each source gets:
- A `copy_from_<source>.py` helper (thin wrapper)
- Connector-specific NE2xxx error codes
- A `docs/site/guides/ingest-from-<source>.md` user guide
- Upgrade smoke test in `tests/upgrade_smoke/test_dlt_<source>.py`

**Sources for v0.3** (by demand):
1. REST APIs (`nucleus ingest rest+json://api.example.com/endpoint`)
2. Google BigQuery (read)
3. AWS S3 / Parquet files direct
4. CSV / NDJSON files (local and S3)
5. Google Sheets (via dlt)
6. Salesforce (via dlt verified source)

**Per-connector ADR**: Each connector gets an ADR (ADR-014 pattern). ADR number assignment: 019, 020, 021...

**Effort**: ~150 LOC per connector; 6 × 150 = ~900 LOC. Plus ~100 LOC common dispatch refactoring.

### 5. `nucleus_project.yaml` Strict Validation

**Why**: Malformed `nucleus_project.yaml` (wrong catalog type, missing required fields) currently produces cryptic errors deep inside pyiceberg. Validate at startup.

**What**:
- Pydantic or `dataclasses` schema for `nucleus_project.yaml` (no new dependency — Pydantic may already arrive via FastAPI/dlt)
- `nucleus up` validates YAML on startup; detailed error with line number if invalid
- Error: `NucleusEnvironmentError` (NE5001) with field name and expected type

**Effort**: ~100 LOC.

### 6. AI Copilot Multi-Provider Routing (ADR-015 evolution)

**Why**: Some teams can't use OpenAI (data residency, cost). LiteLLM already supports 100+ providers — expose the routing explicitly.

**What**:
- `NUCLEUS_COPILOT_PROVIDER` env var (e.g., `anthropic`, `ollama/llama3`, `azure/gpt-4`)
- `nucleus chat --provider <name>` override
- Validated at startup; `NucleusAIProviderError` (NE4003) if provider unreachable

**Effort**: ~30 LOC in `intelligence/copilot.py`. LiteLLM already supports this via model string routing.

### 7. Lakekeeper REST Catalog (ADR-004)

**Why**: Filesystem catalog doesn't support multi-user access or production-grade catalog features. Lakekeeper adds REST-standard catalog for multi-engineer teams.

**What**:
- `nucleus enable lakekeeper` — sets up Lakekeeper in `docker-compose.yml` + updates `nucleus_project.yaml`
- pyiceberg `RestCatalog` configuration pointing to Lakekeeper
- Smoke tests: table create + read + snapshot through Lakekeeper

**Swap interface preserved**: user code sees the same `ctx.sql`, `ctx.copy_from`, `@nucleus.asset` — no changes.

**Effort**: ~200 LOC in `coordination/catalog.py` + Docker compose + config handling.

**ADR**: ADR-004 moves from PROPOSED to ACCEPTED.

### 8. Marimo Notebook Integration (v0.3+)

**Why**: Data engineers want to explore assets interactively without leaving the Nucleus stack.

**What**:
- `nucleus notebook <asset-key>` — opens a Marimo notebook pre-loaded with `ctx.read(<asset-key>)`
- Marimo is optional extras: `pip install nucleus[notebook]`
- Marimo reactive cells work with Polars DataFrames returned by `ctx.read`

**Acceptance**: `nucleus notebook my_asset` opens a Marimo UI with the asset's latest snapshot loaded.

**Effort**: ~150 LOC. Marimo is a Python package; no custom integration needed beyond the CLI command + `ctx.read` bridge.
