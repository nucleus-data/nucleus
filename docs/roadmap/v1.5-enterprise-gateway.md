# v1.5 — Enterprise Gateway

> **Codename**: Enterprise Gateway
> **Target**: 2028 H1
> **LOC ceiling**: 30,000 (ceiling reached)
> **Persona**: Mid-enterprise data domain teams (50-200 engineers)
> **Theme**: Mid-enterprise adoption — auth federation, audit, multi-env (dev/staging/prod targets).

---

## Theme: "Mid-Enterprise Teams Can Adopt Without Risk"

v1.5 is when Nucleus targets the data domain team at a mid-market company: they have a real IT security team, they need SAML/SSO, they need dev/staging/prod environment separation, and they need compliance-grade audit logs.

This phase is NOT about competing with enterprise data platforms. It is about making it easy for the startup beachhead teams (who've grown to 50+ engineers) to keep using Nucleus as they mature.

---

## Features

### 1. SAML/OIDC Federation at Enterprise Grade

- SAML 2.0 IdP integration (Okta, Azure AD, Ping Identity, etc.) for cloud tier
- SCIM user provisioning (auto-create/disable accounts from IdP)
- Per-group asset access policies (read-only vs. write per asset key prefix)
- All per ADR-010; no custom auth system — always delegate to the IdP

### 2. Multi-Environment Project Layout (dev/staging/prod)

- `nucleus_project.yaml` gains `environments:` block
- `nucleus run --env staging` — materializes against staging catalog + storage
- Promotion workflow: `nucleus promote <asset> --from staging --to prod`
- Per-environment secrets (Vault or AWS SSM namespaced by env)

### 3. Advanced Audit Log (Compliance-Grade)

- Immutable audit trail (cloud: append-only S3 Object Lock; OSS: advisory)
- Per-asset read access tracking (who queried what, when)
- Export to SIEM (Splunk, Datadog, etc.) via OpenTelemetry log bridge
- `nucleus audit export --format siem --since 2027-01-01`

### 4. Differential Privacy Primitives (Preview)

Per `docs/specs/nucleus_architecture_v4.1.md` §1.2 trend 7:

- `@nucleus.check(privacy="dp-epsilon-0.1")` — differentially private aggregation check
- Integrates with OpenDP or PipelineDP (`# NEEDS VERIFICATION — check library maturity at v1.5 design time`)
- Preview tier (Beta); not recommended for regulated industries without legal review

### 5. Vertical Packs (Preview)

Per `docs/specs/nucleus_architecture_v4.1.md` §18.6:

- Finance pack: pre-built assets for P&L, cash flow, ARR/MRR analytics
- Healthcare pack: HIPAA-aware templates, PHI field tagging, de-identification checks
- Retail pack: inventory, sales velocity, demand forecasting templates
- Each pack is a `pip install nucleus-pack-<vertical>` (separate package; not in core 30K LOC budget)

### 6. Replay + Time-Travel Debugger (Full Version)

Per `docs/specs/nucleus_architecture_v4.1.md` §7.6:

- Every run snapshotted: code git hash + input snapshots + config + output
- `nucleus replay --run-id <id>` — replay any historical materialization
- `nucleus run --debug-snapshot <id>` — run current code against a historical input snapshot
- Cost estimate before replay (ties into Cost Meter from v0.5)

### 7. Streaming Support (Benthos / Redpanda)

- `@nucleus.asset(trigger="streaming")` — continuous ingestion from Kafka/Redpanda topic
- Wraps Benthos (Go-based, Apache 2.0) for stream processing; no JVM
- Iceberg streaming writes via pyiceberg `append` in micro-batches
- Swap interface: `docs/swap/streaming.md` — Flink as the swap target

## 30K LOC Ceiling — Final Phase

v1.5 is the last phase before the 30K LOC ceiling is reached. At this point:

1. The proprietary code budget is exhausted.
2. Future features require either: removing old code (refactoring) or offloading to separate packages (vertical packs, connectors).
3. The `scripts/loc_budget.py` ceiling triggers a STOP condition if exceeded.

**What this means for contributors**: Every new LOC must remove an equal or greater number of old LOC. The 30K ceiling is a wall, not a target.

---

## What Is NOT in v1.5

- Multi-tenant SaaS at scale (v2.0+)
- Data Product Marketplace (v2.0+)
- Global multi-region infrastructure (v2.0+)
- Any feature that pushes past the 30K LOC ceiling without removing equivalent old code
