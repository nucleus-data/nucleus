# Demo reset policy — `demo.nucleus-data.dev`

This document is the **public-facing contract** for what happens to data
generated, queried, or accidentally typed by visitors to the Nucleus public
demo.  It is linked from the Workbench footer at
`demo.nucleus-data.dev/about` so any visitor can read it before submitting
a query.

> **Short version**: every 24 hours the demo wipes any in-process state
> and rebuilds from the same baked-in synthetic e-commerce dataset.  No
> visitor query, no visitor SQL, no visitor click is retained.  Use the
> demo to evaluate Nucleus; do not use it to host your own data.

## 1 — Why we reset

The demo is a **shop window**, not a sandbox.  Three reasons:

1. **Predictable evaluation**: every HN / Reddit visitor sees the same
   numbers in the same charts.  If user A's query reshapes a table user B
   then sees, demo "lessons learned" articles cite wrong data.  Resetting
   guarantees byte-identical state across sessions.
2. **Cost cap**: an unbounded warehouse on a 512 MB Fly machine eventually
   crashes.  Resets prevent slow accumulation regardless of who triggered
   it.
3. **Privacy by design**: nothing the visitor entered survives the wipe.
   This is much simpler than implementing real data-retention policies.

## 2 — What the reset does

A nightly cron (Fly cron via `fly machine run`, or Render cron job —
configured at deploy time; not in the image itself) runs:

1. `fly machine restart` (or `render service restart`) — drains live
   connections and restarts the container.
2. Container starts fresh from the immutable image.  The seeded Iceberg
   warehouse at `/opt/nucleus-demo/data/warehouse` is **read-only at the
   filesystem layer** (`chmod 0444`), so the restart is the only way to
   "reset" — there is nothing to actively wipe inside the warehouse.
3. The run-history ring buffer (in-process, max 200 entries — see
   `src/nucleus/workbench/api/runs.py` line 49) is destroyed implicitly
   by the restart.  No entries are persisted; no entries leak across the
   reset boundary.
4. The lineage events file (`.nucleus/lineage/events.jsonl`) is gone too,
   for the same reason.

Reset cadence: **24 hours**, configurable in the Fly cron schedule.  See
the founder runbook in `docs/release/public_demo_deploy_plan.md` §9 step 9.

## 3 — What data the demo generates (no PII)

The dataset is generated by `deploy/seed_demo_data.py` from a fixed seed
(`random.seed(42)`) at image build time:

| Table             | Rows   | Columns                                                                       |
|-------------------|--------|-------------------------------------------------------------------------------|
| `raw.products`    | 500    | `product_id`, `name`, `category`, `price_usd`                                 |
| `raw.customers`   | 1,000  | `customer_id`, `name`, `country`, `signup_date`                               |
| `raw.orders`      | 10,000 | `order_id`, `customer_id`, `product_id`, `quantity`, `order_date`, `status`   |

Every name is composed from a hard-coded list of synthetic given names
(e.g. `Avery`, `Blake`, `Casey`) + synthetic family names (e.g. `Anders`,
`Brooks`, `Chen`).  No real person is referenced.  No real email, phone,
address, or identifier is generated.

The `country` column draws from a 12-country list of ISO-3166 codes.  No
country is associated with a real customer.

`signup_date` and `order_date` are uniformly distributed within the last
2 years and 1 year respectively, anchored to the demo's build date for
reproducibility.

The total dataset on disk: roughly 600 KB CSV → 250 KB Parquet → 400 KB
Iceberg metadata.  Fits trivially in the Fly free tier.

## 4 — What we log

The demo emits structured JSON logs to stdout (captured by Fly / Render
log streams).  Each log line includes:

| Field          | What it is                                                         |
|----------------|--------------------------------------------------------------------|
| `timestamp`    | ISO-8601 UTC timestamp at log emit.                                |
| `level`        | `info` / `warn` / `error`.                                         |
| `event`        | Short event name (e.g. `query.executed`, `health.ok`).             |
| `route`        | HTTP route hit, if applicable (e.g. `/api/query`).                 |
| `status_code`  | HTTP response status code.                                         |
| `duration_ms`  | Request duration in milliseconds.                                  |
| `ip_hash`      | SHA-256 of the visitor IP + a daily-rotating salt (NOT the raw IP).|

What we **never** log:

- Raw IP addresses.
- The SQL string a visitor submitted to `/api/query`.
- Result rows.
- User-agent strings (beyond a coarse class: `browser` / `bot` / `cli`).
- Cookies, headers, or session tokens.

The `ip_hash` is one-way and rotates daily, so the same IP visiting on
day 1 and day 2 produces *different* hashes.  This means we cannot trace
a person across days; we can only count rough abuse signals within a day.

Logs retain for **7 days** on the hosting platform (Fly free tier
default).  Cloudflare access logs, if enabled, retain per your Cloudflare
plan — note that Cloudflare CAN see raw IPs at the edge; that data is
outside our control and outside this policy's scope.

## 5 — Opt-out for visitor query logs

Visitors who do not want even the redacted `query.executed` log entry can
send the header:

```http
X-Nucleus-No-Log: 1
```

When this header is present, the Workbench (v0.2.1+) skips the
`query.executed` log emission.  The request still runs; only the
log line is suppressed.

Until v0.2.1 ships the header-honoring middleware, the opt-out is best
served by **not submitting a query at all** — the demo's read-only
endpoints (`GET /api/assets`, `GET /api/runs`) emit only a generic
`route.hit` log line with no per-request payload.

To request data removal regardless of method (we're not aware of any
data we could remove, given the `ip_hash` design — but if you believe
otherwise), email the project maintainer at the address listed in
`pyproject.toml` `[project.authors]`.

## 6 — Abuse handling

The demo is intentionally rate-limited and has a single-machine
concurrency cap (50 concurrent requests; see `deploy/fly.toml`
`http_service.concurrency`).  Cloudflare is recommended in front for
per-IP rate limiting (60 req/min/IP — `public_demo_deploy_plan.md` §5).

If an attacker overwhelms the demo:

1. The Fly machine auto-stops; cost stays bounded.
2. The kill switch (`fly scale count 0`) drains traffic in seconds.
3. Cloudflare can deny the offending IP at the edge.

No visitor data is at risk because there is no visitor data to risk.

## 7 — Changes to this policy

This document lives in version control at `deploy/RESET_POLICY.md`.
Any change is a `git` commit visible at the project's GitHub repo.  No
silent policy changes are possible.

When a material change ships (e.g., we start retaining logs longer, or
add Sentry for error tracking), we will:

- Update this document.
- Update the Workbench footer link target.
- Mention the change in the `CHANGELOG.md` entry for the demo image
  version.
